#3 - Structured Fitness Activity Library
What & Why
Replace the narrow Move model with a rich activity knowledge library covering gym, bodyweight, Ashtanga Vinyasa yoga, CARs/joint mobility and conditioning. Separate activity identity and supported measurements from routine/day prescriptions and actual performance. Proposed architecture: PostgreSQL for the shared versioned catalog, offline catalog caching, and local-only personal data; future semantic retrieval remains separate.

Done looks like
Library uses Activity as its umbrella term and specific labels for exercise, asana, mobility drill, conditioning activity and sequence. Workout/session refers to the assembled practice, not a library entry. Replace misleading Move copy throughout relevant flows.
Library definitions have no user dosage fields: sets/reps/seconds/breath counts/distance/load/rest belong to routine or dated plan items, with actual results separate. Definitions declare supported metrics and units; optional reusable prescription presets live separately and are never intrinsic activity facts.
Adding from library to routine, date, or active session opens a type-appropriate target editor. Support reps, duration, breath count and distance with explicit distance units, optional load kg/lb, sets, rest and laterality where applicable, across editing, execution, history and export/import. Do not silently equate breaths with seconds; disclose estimation assumptions or unknown duration.
Target at least 330 substantive, distinct source-backed entries: 200 gym/home/bodyweight exercises combined, 80 Ashtanga-related asanas/practice elements, 35 CARs/joint-mobility drills, and 15 conditioning activities. These are minimum coverage targets, not caps or verified counts of a tradition. Entries may have multiple tags but count once. Establish a source-backed inventory before authoring; never pad counts with synonyms or invented variants, and explicitly report evidence gaps.
Broaden Ashtanga Vinyasa coverage beyond Primary Series: include standing/finishing practices and source-supported Intermediate/Advanced entries where adequate references exist. Store Sanskrit/transliterated and English names, searchable aliases, lineage/source-qualified series/sequence context, supported breath/duration tracking, modifications and instruction-needed flags. No claim of exhaustive coverage or one universally authoritative sequence; advanced entries remain available for browsing without automatic beginner recommendation.
CARs (Controlled Articular Rotations) are a first-class mobility family. Cover source-supported joint-specific drills and meaningful variations, with joint/action, position, stabilization, compensation cues, comfortable range guidance, intensity cautions and regressions. Distinguish general CARs education from proprietary Kinstretch programming; do not imply affiliation, certification or reproduce licensed curricula. No aggressive end-range or injury-rehabilitation prescriptions.
Sequence entries reference ordered activity IDs, preserve repetition and side, and are distinct from individual asanas. Users can inspect and add sequence contents to a routine/day with explicit editable prescriptions; cycles, dangling references and duplicate identity aliases are validated.
Rich detail pages show description, setup and execution, cues, common mistakes, intended benefits with evidence/source qualification, precautions, instruction-needed flags, equipment, difficulty, muscles (primary/secondary where relevant), joints/actions, movement patterns, laterality, and linked variations. Unknown/not-applicable fields are explicit rather than fabricated.
Search works with Sanskrit/English aliases and filters by discipline/type, muscles, joints, equipment, difficulty and supported measurements. Expanded equipment choices also work in profile and adaptation; joint-loading metadata is not mistaken for benefits or diagnoses. Custom activities can use the same schema, with explicit user-authored/unreviewed status and archival.
Shared catalog lives in PostgreSQL through the existing API/database packages, with stable IDs, schema/content versions, controlled vocabularies, typed relationships, ordered sequence membership and source records. Use normalized fields for identity/relationships and validated structured data for type-specific attributes. Add indexes and normal text/alias search; prepare deterministic retrieval text as derived output, but no embeddings or vector service yet.
App ships a validated starter catalog snapshot and atomically caches complete versioned catalog releases. It remains usable on first offline launch and when updates fail; retain last-known-good data, show freshness/update errors, reject incompatible releases, and preserve archived references. Catalog updates never overwrite personal prescriptions or historical snapshots.
Personal custom activities, routines, schedules, active workouts and history stay local; do not upload health-related data or introduce login/cloud sync. Public API exposes only released shared catalog data, validates query inputs and bounds results; database credentials stay server-side. Catalog writes are restricted to trusted maintainer tooling, with no public unauthenticated write endpoint.
Provide validated, idempotent catalog import/release tooling with dry-run checks, explicit target environment, review status, provenance, release versioning and rollback to a previous published catalog release. Document development versus production content loading separately from schema deployment; seed data must not be assumed to copy automatically. No production schema scripts or startup DDL; read the database skill before implementation. A standalone admin UI is not required.
Source records include URL/title, provenance, retrieval/review dates when actually known, permitted-use/license notes, and content review status. Original instructional wording and properly permitted assets only; no copied competitor databases or unsupported medical benefits. Built-in does not mean clinically verified.
Existing custom definitions, routines, scheduled copies, active sessions and history migrate without loss; existing numeric values become prescriptions rather than being discarded. Catalog edits never rewrite saved schedules/history. Unsupported or inconsistent imports show actionable errors.
Adaptation preserves chosen activities, locks and safety exclusions. Newly expanded or advanced entries are not automatically eligible merely because they exist; unknown metadata never counts as safe. No automatic rehab prescriptions or advanced yoga progression.
Fix existing numeric-draft bug: typing a target then immediately saving preserves the displayed value, and stepping after typing uses that value. Fix explicit zero-load logging/resume so a zero-weight set does not restore an older weighted set; retain its unit.
Out of scope
Cloud accounts or personal-data sync, vector database deployment, embeddings/LLM calls, AI coaching, clinical validation or treatment claims, automatic progression, licensed media acquisition and claims of exhaustive advanced Ashtanga coverage. No broad visual redesign or standalone admin interface.

Steps
Establish the activity taxonomy, supported measurement contract, separate prescriptions and source/review model; inventory reputable, usable sources and coverage for the catalog. Read relevant Expo and frontend guidance before implementation.
Implement the versioned schema and lossless local-data migration, decouple the legacy generated-session engine from catalog dosage, and protect immutable snapshots and import/export compatibility.
Implement the database-backed shared catalog, read API, maintainer import/release tooling and atomic offline cache with a bundled initial snapshot. Author and validate the broad catalog, CARs family, aliases and sequences using source-qualified instructional and safety information.
Upgrade library search, filters, detail pages and custom editing, then integrate target selection into routines, calendar and mid-session additions with measurement-specific execution/history.
Integrate conservative adaptation and duration estimation, fix numeric commit/stepper and zero-load recovery defects, and keep actuals independent of planned targets.
Verify catalog counts/coverage, references, aliases, migrations, metric/unit round trips, snapshot immutability, adaptation exclusions, release validation and offline/update-failure behavior. Run one focused browser journey covering catalog discovery, prescription, save/reopen and logging; test API restrictions with focused requests.
